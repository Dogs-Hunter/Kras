# Aeroporty 1.0.0 — финальный отчёт о релизе

Дата выпуска: **2026-10-12**  
Каталог релиза: `output/release/`  
Статус: **готов к сдаче**

## 1. Соответствие исходному заданию

Релиз содержит мировой набор объектов с ICAO, прошедших строгую проверку полноты. Для каждого аэропорта присутствуют ICAO, latitude, longitude, status (`open`/`close`), type, country, elevation в футах, IANA timezone, число физических ВПП, уникальный ID и name. Для каждой ВПП присутствуют ID, положительная length в футах и surface.

JSON, TOML и YAML используют вложенную модель `airport -> runways`. CSV содержит одну строку на физическую ВПП и повторяет поля аэропорта; provenance и evidence сериализованы в JSON-колонки. Обратное чтение CSV восстанавливает ту же модель без потерь. Аэропорты с несколькими ВПП сохраняют каждую физическую полосу, её длину, покрытие и обозначения концов.

Проект не заявляет охват всех аэропортов планеты: объект включается только при наличии ICAO, всех обязательных значений и хотя бы одной полностью описанной наземной ВПП.

## 3. Источники и актуальность

- OurAirports `airports.csv`, `runways.csv`, `countries.csv`: закреплённый снимок с HTTP `Last-Modified` 2026-10-09;
- FAA/NASR APT: выпуск с датой вступления в силу 2026-10-01;
- ANAC Public/Private V2, SIROS и диагностические таблицы: immutable snapshot `2026-10-11`;
- FAA airport diagrams/procedure publications и ANAC Portaria 18.582/SIA с LCA: доказательства для восьми разрешённых конфликтов;
- IANA timezone polygons: bundled database `2026d` через `tzf-rs`.

URL, время получения, условия использования и решения об интеграции записаны в `output/release/manifest.json`. Исторические ANAC-таблицы используются как наблюдения, но не повышаются автоматически до текущих фактов.

## 4. Качество обязательных атрибутов

Финальный валидатор подтвердил:

- уникальность всех 10 573 ICAO и ID;
- допустимые координаты WGS84, типы аэропортов и непустые страны;
- измеренную высоту с source evidence для каждого аэропорта;
- синтаксически корректную IANA timezone;
- документированное evidence для `open`/`close`;
- точное совпадение `runways_count` с массивом ВПП;
- положительные длины и известные невода-покрытия всех 14 259 полос;
- отсутствие helipad, waterway, unknown/invalid и дубликатов ВПП в строгом экспорте;
- наличие разрешённого evidence для всех 159 080 обязательных позиций;
- наличие provenance у всех аэропортов и ВПП.

`validation_report.json` содержит машинный результат каждой проверки с нулевым числом ошибок.

## 5. Независимые подтверждения и ограничения

`IndependentlyVerified` означает согласование поля с действительно независимым источником. Синтаксическая проверка, round-trip форматов, timezone-вычисление и согласование таблиц одной базы независимым подтверждением не считаются.

Все восемь конфликтов Phase 5 повторно проверены по итоговой модели. У каждой исправленной длины сохранились как выбранное `Recovered` evidence, так и прежнее историческое свидетельство `NotComparable`; устранение конфликта не уничтожило историю.

Ограничения:

- глобальная часть за пределами покрытия FAA/ANAC в основном зависит от OurAirports;
- `status=open` не заменяет NOTAM и не гарантирует текущую эксплуатационную доступность;
- 230 публичных и 25 частных кандидатов ANAC не включены из-за отсутствия текущих обязательных данных;
- набор не предназначен для оперативной аэронавигации;
- обновление текущих источников может закономерно дать результат, отличный от релиза 1.0.0.

## 7. Воспроизводимость

Команда зафиксированного воспроизведения:

```powershell
cargo run --release -- run --offline
cargo run --release -- release
```

Phase 5 проверяет SHA-256 всех 21 файлов baseline Phase 4, manifests FAA/ANAC, официальный evidence cache и независимый JSON ANAC. `release` заново читает модель, выполняет аудит, экспортирует все форматы во временный каталог, проверяет round-trip и только после успеха атомарно публикует `output/release/`.

Кэш источников и immutable результаты ранних фаз исключены из Git из-за размера. Полный список файлов, которые требуется сохранить отдельным архивом для offline-пересчёта, приведён в `REPRODUCIBILITY.md`. Без внешнего архива Git-репозиторий позволяет собирать и тестировать код, проверять готовый релиз и повторять его внутренний аудит, но не пересчитывать его от исходных snapshots.

## 8. Состав Git-репозитория

Локальный репозиторий инициализирован на ветке `main`. Commit и push не выполнялись.

В Git предназначены:

- `src/`, `tests/`, `Cargo.toml`, `Cargo.lock`;
- `README.md`, `REPRODUCIBILITY.md`, `LICENSE`;
- `data/phase5_conflict_evidence.csv`, `data/phase5_baseline.json` и небольшая примерная фикстура;
- `audit/`, включая этот отчёт;
- `output/release/` с четырьмя экспортами, manifest и validation report.

Исключены `.gitignore`:

- `target/`, `tmp/`, coverage, логи и атомарные `.part`/`.tmp`;
- локальный `cache/` и сторонние архивы/PDF;
- `output/candidate-phase*` и прочие промежуточные результаты;
- локальный `data/enrichment.json`, `.env`, ключи и редакторские файлы.

Проверка prospective Git-состава не обнаружила секретов. Ни один релизный файл не превышает 100 MiB, поэтому Git LFS не применён. Общий объём четырёх экспортов около 275,75 MiB; перед сдачей следует убедиться, что учебная Git-платформа допускает такой общий размер репозитория.

## 10. Известные ограничения

Блокирующих дефектов не обнаружено. Неблокирующие ограничения связаны с неполнотой мирового базового источника, региональностью официальных проверок, невозможностью трактовать `open` как оперативный статус и необходимостью отдельно хранить крупные исходные snapshots для полного offline-пересчёта.

## 11. Проверка преподавателем

```powershell
git status
cargo test
cargo build --release
cargo run --release -- validate --output output/release
cargo run --release -- release
```

Затем следует проверить `output/release/manifest.json`, `output/release/validation_report.json` и сравнить SHA-256 четырёх экспортов с таблицей выше. Для полного пересчёта из источников нужно сначала восстановить внешний snapshot archive по инструкции `REPRODUCIBILITY.md`, после чего выполнить `run --offline`.
