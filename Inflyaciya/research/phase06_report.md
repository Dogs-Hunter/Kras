# «Инфляция» — отчёт Phase 0.6: официальный MCP ВкусВилла

Дата проверки: **10 октября 2026 года (Europe/Moscow)**.

## Резюме и решение

Rust-клиент подключился к официальному `https://mcp.vkusvill.ru/mcp` по MCP Streamable HTTP, выполнил `initialize`, согласовал версию протокола **2025-03-26**, отправил `notifications/initialized`, получил фактические схемы 10 инструментов и вызвал разрешённые read-only инструменты.

Анонимный источник практически пригоден для наблюдения **общих (`Generic`) цен**: получены 30 реальных товаров из 10 поисковых групп, числовые цены, ID/XML ID, ссылки, категории, вес/объём и скидки. Один и тот же товар `36296` в двух новых MCP-сессиях сохранил ID и цену 100 ₽. Это проверка в один день, а не гарантия долговременной стабильности.

Главное ограничение не устранено: ни физический магазин, ни адрес доставки не входят в анонимный контекст цены. Авторизованный каталог требует предварительной регистрации OAuth-клиента и согласия пользователя; этого действия без участия пользователя не выполнялось. Поэтому итог — **вариант B: MCP подходит с ограничениями**, состояние авторизованной части — **`PendingAuthorization`**.

## A. Соединение MCP

- endpoint: `https://mcp.vkusvill.ru/mcp`;
- транспорт: HTTPS POST, JSON-RPC 2.0, `Accept: application/json, text/event-stream`;
- клиент запросил `2025-06-18`, сервер выбрал `2025-03-26`;
- `initialize` → HTTP 200, `notifications/initialized` → 202, `tools/list` → 200;
- сервер: `VV MCP Server`, версия `0.0.1`;
- `Mcp-Session-Id` не возвращён: сервер работал без состояния, поэтому DELETE-завершение не требовалось. Клиент умеет отправить DELETE, если сервер когда-либо выдаст session ID;
- фактические ответы были `application/json`; парсер также поддерживает SSE `data:` и `structuredContent`.

Реализовано раздельное сообщение об ошибках транспорта, HTTP 401/403, HTTP 429, JSON-RPC, `isError`, несовместимой схеме и некорректных данных.

`tools/list` вернул 10 инструментов:

| `vkusvill_product_details` | подтверждён анонимно по ID |
| `vkusvill_products_discount` | подтверждён анонимно, 10 результатов на страницу |

Документация посадочной страницы говорит о корзине на 1–20 товаров, а фактическая JSON Schema допускает `maxItems: 30`. Клиент не использует ни один из вариантов: операция запрещена. В описании `products_search` перечислено поле `available_quantity` для `custom`, но фактический enum `fields` его не содержит; анонимные ответы наличия не дали.

## C. Анонимный доступ

Подтверждены:

- `id`, `xml_id`, название, бренд в подробной карточке, URL;
- `price.current`, `currency`, иногда `price.old`, процент и текст скидки;
- `unit`, `weight`, размеры упаковки в названии;
- category path и `facets.categories`;
- рейтинг, изображения, состав и КБЖУ в подробных режимах;
- пагинация (`page`, `limit`, `total`, `pages`, `has_more`), максимум `limit=10` по схеме.

В ответах поиска стояло `personalized=false`. `available_quantity`, магазин и адрес отсутствовали. Следовательно, все 30 наблюдений имеют `authorization_mode=Anonymous`, `store_binding=Generic`, `store_id=null`, `store_address=null`.

## D. OAuth 2.0 + PKCE

Официальная процедура требует войти на сайт ВкусВилла, зарегистрировать сторонний сервис по `https://vkusvill.ru/oauth/registration/` и получить регистрационные данные по электронной почте. Условия разрешают подключать собственный сервис и указывают, что доступ к личному кабинету может действовать до одного года и может быть отозван.

Discovery проверен без авторизации:

- authorization server: `https://oauth.vkusvill.ru/`;
- authorization endpoint: `/oauth2/auth`;
- token endpoint: `/oauth2/token`;
- revocation endpoint: `/oauth2/revoke`;
- заявлены `authorization_code`, `refresh_token`, device code и другие grants;
- PKCE: `plain` и `S256`; для реализации следует использовать только `S256`;
- resource scopes: `catalog.search`, `purchase_history.read`, `discounts.view`, `recommendations.personalized`.

Форма регистрации за экраном входа не раскрыла допустимые redirect URI, поэтому их правила — `Unverified`. Реальный client ID, пользовательское согласие, обмен code→token, refresh и revoke не проверялись. Токены, коды, cookies и секреты не создавались и не сохранялись. CLI лишь принимает уже существующий access token из `VUSVILL_MCP_ACCESS_TOKEN`; это промежуточный способ без постоянного хранения, не законченный OAuth-flow.

## E. Магазин на Маршала Василевского, 17

Официальная страница `https://vkusvill.ru/shops/?shop_id=5047141` подтверждает магазин по адресу **Москва, ул. Маршала Василевского, д. 17**, метро Щукинская, телефон и режим работы. `5047141` — ID страницы сайта, а не доказанный MCP ID.

`vkusvill_shops` анонимно вернул справочник из 2212 точек и словари регионов, городов, метро и особенностей. В схеме есть `id_region_filter`, `id_city_filter`, `id_subway_filter`, однако передача известных ID Москвы и трёх ID «Щукинская» не изменила `total=2212` и первую страницу. Текстового поиска и запроса по shop ID в схеме нет. Ради исследования не выгружались все 222 страницы.

Итог: существование кандидата подтверждено официальной страницей; нахождение/устойчивый ID через MCP и соответствие `5047141` какому-либо MCP ID — `Unverified`.

## F. Географическая привязка

- **StoreBound — `Unavailable`**: MCP не сообщил физический магазин для цены.
- **AddressBound — `Unverified`**: официальная инструкция говорит, что для актуального персонального каталога после OAuth в кабинете должен быть установлен адрес доставки, но авторизованной проверки не было.
- **Generic — `Confirmed`**: именно так классифицирован весь анонимный эксперимент.

Нельзя заключать, что товар будет собран на Маршала Василевского, 17, или что анонимная цена действует там.

## G. Товары, цены и нормализация

В `phase06_sample_products.json` сохранены 30 позиций: по три результата запросов «молоко», «сыр», «гречка», «макароны», «хлеб», «помидоры», «яблоки», «курица», «лосось», «кофе». Это ограниченная исследовательская выборка, не полный каталог и не корзина.

Для каждой записи сохранены исходная цена, `old`/скидка при наличии, ID/XML ID, URL, category path, исходная упаковка, нормализованное количество и цена, время, инструмент, режим авторизации и географический статус. Поле `package.basis` различает размер из названия (`product_name`), структурированный `weight` (`mcp_weight`) и цену за кг (`mcp_unit_price`). Значения не выдумываются: при отсутствии пригодного размера нормализованная цена должна оставаться `null`.

Все 30 текущих строк удалось нормализовать через `rust_decimal`; две содержат `old` цену. Важно: `weight` сервера может быть технической массой товара, а название иногда противоречит характеристике. Перед переводом наблюдения в `ConfirmedObservation` нужен отдельный контроль согласованности.

## H. Категории и широкий охват

`facets.categories` возвращает пары `category_id/category_name`, а товары — иерархический массив `category` с ID, slug и URL. Поиск технически покрывает молочные продукты, бакалею, хлеб, овощи, фрукты, птицу, рыбу, напитки/кофе и другие группы. Пагинация подтверждена, но полный обход каталога не выполнялся.

Статус структуры категорий — `Partial`: категории и подкатегории видны в результатах, но единое полное дерево и его долгосрочная стабильность не доказаны.

## I. Презервативы

Анонимные поиски «презервативы», `Contex` и `Durex` каждый вернули `total=0`. Поэтому товары, цена за упаковку и ₽/шт. через MCP не получены. Статус — `Unavailable` для проверенного анонимного режима; после OAuth это следует проверить повторно, не предполагая положительный результат.

## J. Алкоголь

Поиски «пиво», «вино», «алкогольное вино», «водка», «водка коньяк виски» не дали подтверждённого алкогольного товара. Результаты были безалкогольными напитками, водой, виноградом или нерелевантными товарами. Они не были выданы за алкоголь. Возрастные ограничения не обходились.

Статус настоящего алкоголя — `Unavailable` в анонимном MCP. Это не делает весь источник непригодным.

## K. Воспроизводимость и ограничения

Товар `36296` («Молоко 2,5% в бутылке, 900 мл») найден поиском и затем дважды запрошен по ID в двух отдельных процессах/новых MCP-сессиях. Оба ответа: `id=xml_id=36296`, `price.current=100`, без наличия. Два одинаковых поиска «молоко» также дали одинаковые первые пять ID и цен.

Для еженедельного запуска подтверждена техническая повторяемость **Generic**-наблюдений. Не подтверждены недельная устойчивость ID, адресный контекст, персональные скидки, лимит запросов и поведение при истёкшем OAuth. Нагрузочный тест не проводился; клиент ограничивает страницу десятью товарами, имеет timeout и отдельно распознаёт 429.

## L. Архитектура Rust-прототипа

Добавлены модули `mcp/client.rs`, `models.rs`, `auth.rs`, `products.rs`. Клиент не требует LLM и не использует скрытые endpoint. CLI поддерживает `ping`, `tools`, `search`, `details`, `barcode`, `discount`, `shops`, `repeat`, `sample`, `auth-status` и `--help`.

Операции корзины, истории заказов и персонального «Любимого продукта» не входят в read-only allowlist. Старые режимы Phase 0 и Phase 0.5 сохранены. Следующий production-слой должен явно реализовать конвейер `SourceAdapter → CandidateObservation → Validation → ConfirmedObservation`: текущие MCP-записи остаются кандидатами, пока нет доказательства географии и согласованности упаковки.

Локальные фикстуры покрывают JSON/SSE/structured MCP, список tools, JSON-RPC error, цены, массу/объём/штуки, неверные ID и отсутствие товара, ошибочную упаковку, анонимную модель, три статуса географии, 401/403, 429, изменение схемы и запрет секретов. Интернет и OAuth для unit-тестов не нужны.

## M. Окончательное решение

Выбран **B — MCP подходит с ограничениями**.

MCP можно рассматривать как основной автоматический источник общих цен и характеристик на следующем исследовательском шаге. Для исходной цели «цена выбранного физического магазина» его пока недостаточно. До Phase 1 нужны:

1. регистрация OAuth-клиента самим пользователем;
2. реализация authorization code + PKCE S256 с защищённым хранилищем Windows;
3. пользовательское согласие только на минимальные scopes (без истории покупок);
4. установка тестового адреса в личном кабинете и проверка `AddressBound`;
5. повторение магазина, презервативов, алкоголя и цен до/после OAuth;
6. недельный пилот на небольшой фиксированной панели ID с фиксацией изменений схемы и 429.

До этих проверок состояние OAuth — `PendingAuthorization`, StoreBound — `Unavailable`, AddressBound — `Unverified`.
