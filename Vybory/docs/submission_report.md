# Технический отчёт по проекту Vybory

## 1. Цель работы

Целью работы было создание программного средства автоматизированного сбора, проверки и экспорта протоколов участковых избирательных комиссий из официального источника.

## 2. Постановка задачи

Для выборов депутатов Государственной Думы Российской Федерации IX созыва 20 сентября 2026 года требовалось получить протоколы № 2 по федеральному избирательному округу. Итоговый набор должен содержать одну запись на одну уникальную УИК и все 22 обязательных показателя: 12 общих строк протокола и результаты десяти федеральных списков.

## 3. Использованные технологии

Основной pipeline написан на Rust stable. Для асинхронных операций используется Tokio, для HTTP — Reqwest, для SQLite — Rusqlite с встроенной SQLite, для JSON — Serde, для CSV — crate `csv`, для CLI — Clap, для журналирования — Tracing. SHA-256 рассчитывается библиотекой `sha2`.

## 4. Источники данных

Данные получены из структурированного JSON-сервиса официального приложения izbirkom.ru. Программа использует те же разрешённые endpoints и штатный challenge, ограничивает частоту запросов и не исполняет полученный JavaScript. Протокол № 2 запрашивается с `report=242` и `protocolNum=2`.

Для новых запросов сохраняется буквальное тело HTTP-ответа до разбора. Исторические 89 132 ответа были сохранены как повторная сериализация Rust-модели; это ограничение явно документировано и не скрывается.

## 5. Архитектура

```text
официальный источник → загрузка → парсинг → валидация → SQLite → CSV/JSON
```

Сначала приложение обнаруживает иерархию комиссий и создаёт устойчивую очередь УИК. Полученные ответы разбираются в строгую модель, сопоставляются с запрошенным UUID, проверяются по структуре и арифметике, после чего транзакционно сохраняются в SQLite. Экспорт строится только из текущих строго валидных версий.

## 6. Реализованные возможности

Реализованы рекурсивное обнаружение комиссий, дедупликация УИК, параллельная загрузка с ограничением частоты, кэширование, продолжение после прерывания, хранение версий и происхождения данных, проверка 22 строк, арифметические контроли, независимая сверка агрегатов ТИК, территориальные представления и SHA-256-манифест.

## 7. Результаты

Обнаружено 91 399 УИК. Получено 89 132 полных строго валидных протокола, покрытие составило 97,5196665%. Дубликатов УИК, арифметических ошибок и расхождений с официальными агрегатами не обнаружено. Проверены 2 839 полных ТИК; 101 ТИК не объявлена полностью сверенной из-за отсутствия индивидуальных протоколов части УИК.

Официальный признак повторного протокола установлен у 176 текущих записей. УИК с несколькими физически сохранёнными версиями нет; у всех 176 повторных протоколов предыдущая версия локально недоступна.

## 8. Проверка достоверности

Все 89 132 протокола численно сопоставлены по строкам 1–22 между сохранённым JSON, SQLite и CSV. Внешняя выборка из 54 УИК повторно совпала с официальным API по всем числам и report ID. Для 2 839 полных ТИК отдельно получены, сохранены и сопоставлены официальные агрегаты. Контрольное изменение одной строки во временной базе было обнаружено механизмом сверки.

## 9. Ограничения

Через проверенный индивидуальный endpoint недоступны 2 267 протоколов: ДНР — 764, ЛНР — 651, Запорожская область — 659, Херсонская область — 193. На внешней выборке получен HTTP 404, однако это не доказывает, что протоколы никогда не публиковались. Диагностический статус — `Unknown`. Агрегаты 101 ТИК нельзя использовать для восстановления отдельных УИК, поэтому значения не вычислялись и не подменялись нулями.

Адреса УИК надёжно не извлекаются из проверенного интерфейса. `signDateTime` отсутствует у текущих протоколов, поэтому `protocol_date` остаётся пустой. Поле `createdAt` обозначено в официальном клиенте как дата генерации и экспортируется под точным именем `source_created_at`, а не как дата публикации.

## 10. Вывод

Реализован воспроизводимый сборщик и проверенный датасет протоколов № 2 с сохранением структуры, числовых значений и происхождения. Получена максимально полная выборка из доступного индивидуального интерфейса — 89 132 протокола из 91 399 обнаруженных УИК. Оставшееся ограничение связано с доступностью 2 267 индивидуальных официальных ответов и не устранялось предположительными вычислениями.
